The one thing that matters

There are two pull requests and they must merge in this order. PR 1 is safe at any time. PR 2 deletes the files that www.zeliade.com is currently served from — merging it before GitHub Pages has been switched over takes the site offline.

Everything else in this document is detail around that single constraint.

What is changing

The site has been a WordPress export edited as raw HTML: 670 KB of markup carrying about 15 KB of actual text, with the header, footer and menu duplicated across all eleven pages. Changing a phone number meant eleven edits.

It is now built from structured content. Text lives in Markdown and YAML files, validated against a schema, and the pages are generated from them. Adding a white paper is one small file plus its PDF. Nobody edits HTML.

The two pull requests

Safe to merge

PR 1 — modernize/astro-site

Adds the new site in site/ plus the build workflow, alongside everything that is already there. 114 files added, nothing removed.

Effect on the live site: none.

Merge last

PR 2 — modernize/remove-legacy

Deletes the WordPress export from the repository root: the scraped pages, the Avada theme, Fusion Builder, the bundled jQuery and the RSS stubs. 319 files removed.

Effect on the live site: removes the files Pages currently serves. Harmless after step 5, fatal before it.

Before you start: run it locally

Nothing below touches GitHub, the live site or the repository. Do this first — it is the cheapest possible way to find a problem.

Check out modernize/remove-legacy, not the other branch. The site/ directory is identical on both, so you see the same website either way — but on remove-legacy the old WordPress files are already gone, which proves the new build does not quietly depend on any of them.

Requires Node.js 22.12 or newer. Check with node --version.

If you do not have Node.js

On macOS or Linux, install it with nvm:

curl -o- https://raw.githubusercontent.com/nvm-sh/nvm/v0.40.1/install.sh | bash
# open a NEW terminal, then:
nvm install 22

On Windows, use the installer from nodejs.org (LTS).

If node --version works but npm says “command not found”, nvm is installed but not loaded in this shell. Either open a new terminal, or run:

export NVM_DIR="$HOME/.nvm"
. "$NVM_DIR/nvm.sh"

npm is itself a Node script, so it needs node on your PATH — not merely present on disk. Adding those two lines to ~/.bashrc makes it permanent.

git fetch origin
git checkout modernize/remove-legacy
cd site
npm ci          # installs exactly the versions in package-lock.json
npm run build   # ~2 s; fails loudly if any content is broken
npm run preview # serves on http://localhost:4321

Open http://localhost:4321 and click through everything — every menu entry, a few white paper PDFs, the team biographies, and an address that does not exist to see the 404 page. Resize the window down to phone width to check the mobile menu.

Use npm run preview, not a plain HTTP server. Serving site/dist with something like python3 -m http.server mostly works, but it returns its own bare error page instead of the site’s styled 404, so that one check would give a misleading result. npm run preview serves the exact files the workflow publishes.

Press Ctrl+C to stop, then git checkout master to get back. Nothing you did needs undoing.

How to complete the merge

  1. Merge PR 1

    Merge modernize/astro-site into master. The live site does not change: Pages is still deploying from the branch root, and every legacy file is still in place.

    Expect one red run. Merging starts the Build and deploy site workflow. It will build successfully and then fail on the deploy step, complaining that Pages is not configured for Actions. That is correct at this point — Pages has not been switched yet. Do not try to fix it.

  2. Check the build job

    Open the failed run, open the build job, and confirm three lines:

    ✓ 31 logo, 12 PDF and 5 portrait reference(s) resolved
12 page(s) built
0 errors, 0 warnings, 0 hints

    If the build job itself is red, stop and investigate. Do not continue to step 3.

  3. Switch Pages to GitHub Actions

    Settings → Pages → Build and deployment → Source: GitHub Actions

    Leave the custom domain and Enforce HTTPS alone.

    Downtime begins here. The old deployment stops being served and nothing has been published by Actions yet. Go straight to step 4 — do not stop for coffee.

  4. Run the workflow

    Actions → Build and deploy site → Run workflow (branch master)

    Roughly two minutes. Both jobs must go green. Downtime ends when the deploy job finishes.

  5. Verify on the real domain

    Not on a preview — on www.zeliade.com itself. Every page, plus one PDF:

    • /
    • /zqf/
    • /consulting/
    • /mvccps/
    • /whitepapers/
    • /researchpapers/
    • /clients/
    • /company/
    • /team/
    • /contact-us/
    • /legal-information/
    • /whitepapers/zwp-012-IMforOptions.pdf

    Also check the padlock is present, and that a nonsense address returns the styled 404 page rather than GitHub's.

    This is the decision point. If anything is wrong, roll back now — see Rollback, below. Rollback is free until step 6.

  6. Merge PR 2

    Only now. Pages no longer serves the repository root, so removing those 319 files has no visible effect. This is what makes the change real rather than merely additive.

Rollback

Before step 6 — a settings toggle

Settings → Pages → Source → Deploy from a branch, branch master, folder / (root)

No git operation, no deploy. Every legacy file is still on master, so the old site returns as soon as Pages rebuilds. This is the entire reason the deletion is a separate pull request.

After step 6 — restore the files, then toggle

git revert --no-edit <sha of "Remove the legacy WordPress export">
git push origin master

Then switch the source back as above.

Nothing is ever unrecoverable. The complete WordPress export stays in git history, including the higher-resolution team portraits and the superseded 2009 edition of the SVI calibration white paper.

After the cutover

  • Submit the sitemap — www.zeliade.com/sitemap-index.xml in Google Search Console.
  • One class of link does break. White paper PDFs moved from /wp-content/uploads/whitepapers/… to /whitepapers/… so that no WordPress-shaped address remains. GitHub Pages cannot redirect a .pdf address, so old links to the PDFs will 404. Worth searching for who links to zeliade.com/wp-content and asking them to update.
  • Delete both branches once you are satisfied.

Who edits what, afterwards

No HTML, in any of these cases.

Every one of these is checked against a schema when the site builds. A missing PDF, an unresolvable portrait, a malformed date or a forgotten page description fails the build instead of reaching the live site.
